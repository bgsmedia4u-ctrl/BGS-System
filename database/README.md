# database/ — BGS Teachers & Administration Portal

## What's in this folder

| Path | Purpose |
|------|---------|
| `master_schema.sql` | **The only file to trust** for "what does the database look like today." |
| `migrations/` | Historical SQL files that built the schema incrementally. Already applied. Reference only — do not re-run. |
| `seeds/` | Student roster seed data (Commerce stream). Reference only. |

## Rules

1. **`master_schema.sql` is the source of truth.** If you want to know what
   tables, columns, constraints, RLS policies, triggers, or indexes exist in
   the live Supabase PostgreSQL database, read this file. It was generated by
   consolidating all legacy SQL files on 2026-07-25.

2. **Everything in `migrations/` is historical and already applied.** The
   files are kept for reference (e.g. "which migration added this column?")
   but are not meant to be run again. Their contents may be stale — earlier
   files are superseded by later ones. `master_schema.sql` resolves all
   supersessions.

3. **New changes get new timestamped files.** When you need to change the
   schema, create a new file in `migrations/` following the naming convention:
   ```
   YYYYMMDDHHmm_short_description.sql
   ```
   Example: `202607251030_add_notification_log_table.sql`

4. **After applying a migration, update `master_schema.sql`** to reflect the
   new state. The master schema must always match the live database.

5. **No destructive statements without a human-reviewed backup step.**
   `DROP TABLE`, `DROP COLUMN`, `TRUNCATE` require explicit human sign-off
   and a documented backup step in the same migration file.

## Migration file naming

Files are prefixed with a best-guess timestamp reflecting chronological order
of when they were originally applied:

```
202501010000_initial_setup.sql                   ← supabase_setup.sql
202501020000_marks_module.sql                    ← marks_setup.sql
202501030000_attendance_module.sql               ← attendance_setup.sql
...
```

The timestamps are approximate (the original files had no dates). What matters
is the relative order, not the exact date.

## Appendix: Future/Target Schema (v5–v8)

`master_schema.sql` contains an **Appendix A** section documenting the target
multi-tenant and central identity tables (organizations, institutions, persons,
employees, etc.) from `schema_updates_v5` through `v8`. These tables:

- May or may not be deployed to the live database (not verified during Spec 01)
- Are NOT used by any current application code
- Will be addressed in Spec 02 (identity model migration)

Do not build features against these tables until their deployment status is
confirmed and Spec 02 is complete.
